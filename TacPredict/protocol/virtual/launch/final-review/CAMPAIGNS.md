# Monthly Virtual USDC foundation — inactive

Old deployed private canary's immutable grant budget is 100 Virtual USDC total and already allocated. It has expiry/budget/Merkle claims but lacks scheduled starts and pause/cancel. It cannot be stretched into a public monthly campaign by database edits or UI changes. The new, **undeployed** VirtualPriceAMM adds monthly identifiers, immutable Merkle allocations, future starts/end, total and per-wallet caps, pause/cancel and unused-cap release. It still has a lifetime immutable deployment grant cap, separate from lifetime seed budget. Public amounts, eligibility, liquidity and lifetime budget are not selected or approved by these tests.

No automatic $500 reward, existing-user grant, public claim page or real token transfer. Cancellation stops new claims and releases only unused reserved capacity; it never confiscates or edits a previously granted user balance. Used grants still count against the lifetime cap. One claim per wallet/campaign and domain-bound leaf:

`keccak256(keccak256(abi.encode(engine, chainId, campaignId, wallet, amount)))`

Monthly identifier is keccak256(UTF8 YYYY-MM) in the admin preview. The contract enforces uniqueness of this identifier, not a Gregorian calendar parser; a malicious contract admin could choose a different identifier for the same month. Published configuration and approval controls must enforce the canonical month. Preview validates UTC month boundaries, future start, explicit eligibility, unique normalized nonzero wallets, amount/cap/budget and deterministic sorted-pair proofs. Root binds the actual prospective campaign ID; if another admin publishes first, regenerate and review. Merkle roots prove allowlisting, **not one-person-one-wallet**: anti-Sybil screening/eligibility evidence must be approved offchain, with privacy retention policy, before publication. Do not promise Sybil prevention merely from wallet authentication.

Admin preview/save requires Supabase auth, verified admin role and AAL2 MFA. Capacity is read from the pinned engine; old FPMM deployments are rejected for new monthly features. Preview does not configure/activate an onchain campaign. New `virtual-v2-campaigns.sql` is an additive **migration draft** requiring v1. Service-only atomic draft + audit RPC; authenticated admins can read drafts under RLS, others cannot; no client writes. Draft states are not onchain reward states. Onchain events remain authoritative for published, paused/cancelled and claimed amounts. Admin UI exposes a JSON preview inside existing Virtual Trading cards; polished campaign publication/reporting/control UI and operational signing still need staging integration. No activation button is shipped.

Onchain DEFAULT_ADMIN_ROLE configures/pauses/cancels campaigns. CREATOR_ROLE creates/configures virtual pools; GUARDIAN pauses risk, default admin unpauses. PROPOSER submits feed-derived results, WATCHER disputes, ARBITER adjudicates. App roles never confer these chain roles. Multisig separation and approved role-holder addresses are production gates. No arbitrary user setBalance, withdrawals or real-USDC redemption.

TAC Points use existing version/snapshot/candidate schema and verified event inputs. No formula/weights, reward budget, token mint or distribution activated. QA activity must be explicitly excluded in eventual approved snapshots; private QA evidence is not eligible reward history.
